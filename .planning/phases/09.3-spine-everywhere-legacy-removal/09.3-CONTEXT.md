# Phase 9.3: Spine Everywhere + Legacy Removal (INSERTED)

## Why This Phase Exists

Phase 9.1/9.2 make ingestion/extraction spine-backed and robust.

However, the product still persists critical workflow state to local disk:

- attachments (`backend/attachment_store.py` -> `data/attachments/**`)
- evidence runs + selections (`data/evidence_*`)
- judgments (`data/judgments/**`)
- project meta (`data/project.json`)
- graph stores (SQLite files)

To be distributable and to run cleanly across machines without shared volumes,
these must move to the same spine pattern:

- Postgres tables for durable metadata/state
- object-store artifacts for large blobs

## Primary Goal

The system runs (and can be operated) without requiring any pre-existing `data/**`
directories or local sqlite DBs.

## Graph As Workboard

The graph is expected to become the primary navigation surface once the review
tree exceeds easy working memory. Therefore, graph/workboard state that reflects
reviewer progress (checked marks, roles, assertions, votes, manual edges) must be
durable in Postgres, not local SQLite.

## Ockham Configuration

Minimize configuration knobs:

- Keep `SPINE_MODE=spine` as the only mode switch.
- Delete compatibility flags and filesystem store fallbacks.

## Exit Criteria

- End-to-end review workflow is fully spine-backed:
  - ingest -> extract -> (fallback) -> resolution -> attach -> evidence -> judge -> export
- Deleting `./data` does not break core flows; state persists in Postgres + object store.
