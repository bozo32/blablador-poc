# 10-04.5-01-07 Reading Artifacts: Project-Scoped Spans + Reviewer Opinion Layer

## Goal

Make "reading" produce durable, structurally clean artifacts without mutating canonical machine-owned spans.

Reading artifacts must be:

- project-scoped (multi-project safe)
- reviewer-scoped (per `reviewer_uid` by default)
- exportable/importable (user can delete a project from server and later restore)
- future-proof for a non-Streamlit frontend (no important state trapped in Streamlit)

## Why Now

The POC UI can be janky, but the architecture cannot:

- Canonical extraction/parsing will evolve; annotation anchors cannot be offsets.
- Users will annotate text (highlights/notes/codes) and expect those to be private by default.
- Some reviewer actions must remain visible (e.g. graph validation) while private annotations must remain private (GDPR posture).

## Definitions (Canonical vs Opinion)

Canonical (machine-owned):

- Ingested docs/works, extracted body, reference targets
- Citation-window spans ("citespans") and their index from (doc_id, citation_index, target_id) -> span_id

Opinion (human-owned, reviewer-scoped):

- "follow / ignore / complete" for a citation window
- highlights, notes, and codes applied to a canonical target (span/work/reference/claim/etc.)

Non-goal for this plan: allow mutation of canonical spans. (Elevated authority edits may exist later.)

## Project Scoping Invariants (What this means)

Every endpoint that reads/writes project-owned data must be scoped by an explicit project id.

In practice:

- All relevant API endpoints must accept `X-Project-Id` and use it to select/write rows.
- No implicit "default project" behavior in production paths.
- Cross-project reads must be denied (404) or empty (list endpoints), consistently.

Immediate issue to fix:

- `/spans/*` endpoints are not clearly `X-Project-Id` scoped the way `/ingest/*` and `/attachments/*` are.

## Opinion Layer Requirements (Reading Artifacts)

### Identity

- `reviewer_uid` is derived from institutional login later; for POC we fake it.
- Even in POC, the backend contract must treat `reviewer_uid` as the author/principal for opinion artifacts.

### Privacy + Sharing (Default private)

Policy:

- Default: private (only the owner sees).
- Some behavior is intentionally visible at the project level (e.g. graph votes/edge validation).
- Private annotations (for writing) are not visible to project admins without explicit invitation.

Mechanism:

- Support `visibility: private | shared | public`.
- If `shared`, sharing is by explicit invitation (group-based).

### Groups + Unix-style permissions (seed for /gsd-discuss)

We want per-user ownership but with optional group sharing.

Proposed minimal ACL fields on opinion objects:

- `owner_uid` (reviewer_uid)
- `group_id` (nullable)
- `mode` (e.g. 0600/0640/0660 semantics)
- `visibility` (private/shared/public)

Admin behavior (GDPR posture):

- Project admins can manage membership/invitations.
- Project admins can pull complete views of project-visible graph actions.
- Project admins cannot read private annotations unless the owner explicitly shares.

Open questions for /gsd-discuss:

- Do we need `shared` without groups (per-user allowlist), or is group-only fine?
- Does `public` mean "all project members" or "world"? (Recommend: all project members.)

## Data Model: Single Table vs Per-Object Tables (seed for /gsd-discuss)

User intuition: one table is simpler.

Scale intuition: per-object tables can be easier to optimize later, but are costly to evolve.

Recommendation for POC + lift-friendliness:

- A single opinion-event table with a stable `target_key` and typed payloads.
- Add materialized read models later if needed.

Key concept:

- `target_key` is the join handle to canonical objects (e.g. `span:{span_id}`, `work:{work_id}`, `ref:{doc_id}:{target_id}`).

Minimum fields:

- `project_id`, `event_id`, `created_at`
- `owner_uid`, `group_id`, `mode`, `visibility`
- `target_key`, `kind` (follow|triage|highlight|note|code)
- `payload_json` (stores selector anchoring, note text, code ids, status)
- optional `idempotency_key` for UI retries

## Selector Anchoring Strategy (Required)

Annotations must survive extraction improvements.

Therefore anchors must not be offsets.

Minimum anchor payload (for text-attached annotations):

- quote selector: {exact, prefix, suffix}
- a fingerprint of the window text (or sentence id if stable)
- a canonical target link: `span_id` (preferred) or fallback to (doc_id, citation_index, target_id)

## Export/Import (User-controlled restore)

User story:

- user can export a project, delete it from the server, and later restore by import
- their private/non-exposed artifacts must be removed from server on delete
- their private artifacts must be restorable when they import

Implications:

- Export must include opinion artifacts that the exporting principal is allowed to read.
- Import must rehydrate opinion artifacts without requiring the original Streamlit state.

Open question for /gsd-discuss:

- Should private annotations be encrypted client-side for GDPR-grade separation, or is "server-enforced ACL" sufficient for this POC?

## Workflow Boundary (Reading <-> Chasing)

There is no hard stage break.

Reading and chasing interleave:

- user may chase a cite, come back, and continue reading

We keep the UI tab separation (Document vs Chasing/Review) as representational.

The durable artifact is the opinion record (follow/triage/notes), not a "reading complete" stage.

## Plan of Work (Proposed next executable chunk)

1) Make `/spans/*` explicitly project-scoped
   - require `X-Project-Id` consistently
   - ensure the underlying store selects by project_id (no implicit default)

2) Add a minimal opinion-layer backend for reading artifacts
   - create opinion event table + CRUD-ish API
   - implement: "follow/ignore/complete" for citespans as opinion events (reviewer-scoped)

3) Update Streamlit UI to stop being the source of truth
   - replace `st.session_state`-backed follow queue with server-backed opinion reads/writes
   - keep any UI caches as optional (can be blown away without losing state)

4) Add export/import wiring for opinion events
   - include per-principal readable artifacts in export
   - replay on import

5) Update prune backlog
   - add session-only follow/triage keys as prune candidates once server-backed
