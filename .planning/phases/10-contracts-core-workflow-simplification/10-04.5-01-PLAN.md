# 10-04.5-01 Intake: Unified PDF Drop (Ingest + Attach)

## Goal

From the user’s perspective, “drop a PDF” is a single action.

This plan defines and implements an **Intake** stage that unifies:

- *citing* PDFs (ingest -> extract -> resolve)
- *cited/source* PDFs (attachment pipeline -> promote-ingest -> assign/clone)

…while keeping all durable state in the spine and keeping multi-user correctness.

## Why Now

Current UI splits ingestion into separate, confusing upload controls:

- “Upload documents” (ingest)
- hidden “Advanced: cited source uploads” (attachments)

This prevents a reliable workflow and makes it hard to diagnose failures.

## Intake Contract (Should)

### Inputs

- User supplies 1..N PDFs to the app.
- Optionally: user indicates intent when ambiguous.

### Classification

For each PDF, the app classifies into one of:

1) `citing` (to be reviewed)
2) `source` (to be used as evidence)
3) `unknown` (requires user choice)

Classification heuristics (best-effort):
- If filename/title matches an existing ingested doc: treat as `citing` update (re-ingest) unless user overrides.
- If user currently has a citing doc selected and is in “Review/Chase”: default to `source`.
- If PDF has a large bibliography section + citation callouts: default to `citing`.
- Otherwise: `unknown`.

### Outputs (Durable)

`citing`:
- Ingested document row created/updated (spine).
- Extract+Resolve are triggered per settings.

`source`:
- Attachment row created in spine (global by default).
- Attachment pipeline runs to `matched` or `error`.
- If/when assigned to a claim/target, placement uses **clone** (do not mutate global source).
- If global source is used for doc-level association, it must be promoted to an ingested Work (idempotent).

### Storage / Spine

- PDF bytes must be transferred to the backend and persisted to object store.
- No required reading of UI-local filesystem paths by the backend.

### Multi-user

- All created rows include `project_id` and `created_by_user_id`.
- No shared global “default” behavior in production mode (dev-only defaults ok but must be explicit).

### User Prompts

If `unknown`, app asks:
- “Is this a citing document to review, or a source PDF to cite as evidence?”
- Optional: “Attach to which citing doc / which reference target?” (can be deferred)

## Current Implementation (Does)

UI today:
- `frontend/ui.py`: `render_documents_panel()` provides “Upload documents” -> `/ingest`.
- `frontend/ui.py`: “Advanced: cited source uploads” expander enqueues attachments via `attachment_queue.enqueue_files(...)`.

Attachments today:
- `frontend/attachment_queue.py` persists uploaded files into a Streamlit session temp dir and posts `local_path` to backend.
- This is not web-deployable because the backend can’t read a UI container’s temp path.

## Gap Analysis

- Intake is split across two uploaders; one is hidden.
- Attachments rely on UI-local file paths (non-spine).
- The user cannot see “where a dropped PDF went” (citing vs source) without spelunking.

## Plan of Work

1) Define a single Intake UI entrypoint
- Replace the two uploaders with one “Drop PDFs” block in the left pane.
- Display per-file classification outcome immediately.

2) Eliminate UI-local `local_path` dependency
- Update attachment upload path so backend receives bytes (multipart) or object-store key, not a UI filesystem path.
- Keep a temporary local cache as optional (for local-only “Open PDF”), but not required for matching/evidence.

3) Make Source Inbox first-class
- Show global, unassigned, matched attachments.
- Show errors + remediation actions (retry/promote).

4) Keep placement semantics safe
- Assignments create clones and leave the original global attachment reusable.
- If promotion is needed, do it once and reuse `source_ingest_id`.

5) Add verifier for Intake
- Script that uploads 1 citing PDF and 1 source PDF and asserts:
  - both appear in API listings
  - citing reached extraction+resolution
  - source reached matched
  - source can be assigned twice via clone without mutating the original

## Acceptance Tests

- Uploading a PDF through Intake always results in a visible “bucket” outcome (citing vs source).
- Backend never requires reading a UI filesystem path.
- After restart, both ingested docs and attachments persist and can be used.
- A single source PDF can be reused across two different claims via clone.

## Deliverables

- Code changes for unified Intake UI.
- Attachment upload path that is spine-only.
- `scripts/dev/verify_10_04_5_01_intake.sh`.
- `10-04.5-01-SUMMARY.md` after completion.
