# 10-04.5-09-02 Frontend Retrieval Scope Propagation and Scope-Safe Cache Isolation

## Objective

Align all retrieval-instructions frontend callers to the strict scope contract introduced in `10-04.5-09-01-PLAN.md` and prevent cross-scope dossier bleed by making retrieval cache keying/invalidation scope-aware.

## Non-Negotiable Constraints

- Do **not** add fallback behavior for missing `project_id`/`user_id` in retrieval paths.
- Do **not** silently retry unscoped retrieval requests.
- Do **not** preserve retrieval cache entries across Apply/Switch scope transitions.

## Target Files

- `frontend/ingestion_api.py`
- `frontend/nav_api.py`
- `frontend/claim_queue.py`
- `frontend/components/live_surfing_panel.py`
- `frontend/ui.py`
- `tests/test_frontend_scope_client_guards.py`
- `tests/test_claim_queue.py`
- `tests/test_frontend_scope_selector_lock.py`

## Phase Gates

- **Gate 2.0 (entry):** `10-04.5-09-01-PLAN.md` merged/in-branch; backend retrieval endpoint requires `X-Project-Id` + `X-User-Id` and resolves project strictly.
- **Gate 2.1:** Retrieval API clients cannot issue unscoped retrieval requests.
- **Gate 2.2:** Retrieval UI callsites always pass explicit scope from applied session state.
- **Gate 2.3 (exit):** Retrieval cache is scope-isolated and cleared on scope switch; regression tests are green.

## Phase Tasks

### Task 1 - Enforce scoped retrieval headers in frontend API clients

Implementation:

1. Update retrieval client signatures in both callers to require explicit scope arguments:
   - `ingestion_api.get_reference_retrieval(..., project_id, user_id)`
   - `nav_api.get_reference_retrieval(..., project_id, user_id)`
2. Send strict headers on every retrieval call:
   - `X-Project-Id: <project_id>`
   - `X-User-Id: <user_id>`
3. Preserve fail-closed semantics: if required scope inputs are missing at call time, raise a deterministic client-side error instead of issuing network calls.

Dependency:

- Gate 2.0 satisfied (backend strict contract active).

Verification gate (Gate 2.1):

- Retrieval client unit tests prove headers are sent and unscoped calls are rejected before request dispatch.

Rollback:

- Revert client signature/header changes in `frontend/ingestion_api.py` + `frontend/nav_api.py` together to avoid split contracts.

### Task 2 - Propagate applied scope at all retrieval callsites

Implementation:

1. Update retrieval callsites to pass applied scope explicitly (no hidden defaults):
   - `frontend/claim_queue.py`
   - `frontend/components/live_surfing_panel.py`
2. Use the same applied scope source used by strict sibling endpoints in those surfaces (project + user from active scope state).
3. Preserve existing UX/error rendering behavior, but make missing-scope states explicit and non-retriable without Apply/Switch.

Dependency:

- Task 1 completed (scoped client function contracts available).

Verification gate (Gate 2.2):

- Retrieval from chase/nav surfaces in scoped session sends both headers and no callsite retains legacy unscoped signature.

Rollback:

- Revert callsite plumbing in both files as one unit if surface-specific regressions appear.

### Task 3 - Scope-safe retrieval cache keying and scope-switch invalidation

Implementation:

1. Expand retrieval cache key in `frontend/claim_queue.py` from doc/reference-only to scope tuple:
   - `(project_id, user_id, doc_id, reference_id)`
2. In `frontend/ui.py::_invalidate_scope_cached_state`, clear retrieval dossier cache on successful Apply/Switch:
   - `st.session_state.pop("retrieval_cache", None)`
3. Keep existing invalidations intact; this is additive hardening, not replacement.

Dependency:

- Task 2 completed (scope values present at retrieval entrypoints).

Verification gate (Gate 2.3):

- Scope switch cannot surface stale dossier from previous scope.
- Cache hit only occurs within exact `(project_id, user_id, doc_id, reference_id)` match.

Rollback:

- Revert cache-key and invalidation edits in `frontend/claim_queue.py` + `frontend/ui.py` together.

## Acceptance Criteria

1. Retrieval instructions requests from both ingestion and nav flows always include `X-Project-Id` and `X-User-Id`.
2. Missing scope in frontend retrieval path fails closed before outbound request.
3. Retrieval dossier cache entries are isolated by `(project_id, user_id, doc_id, reference_id)`.
4. Scope Apply/Switch clears retrieval cache and prevents stale cross-scope dossier display.
5. No fallback/default-project behavior is introduced in frontend retrieval flow.

## Manual Verification Checklist

1. Start in Project A, open retrieval instructions for a placed document, confirm success.
2. Switch to Project B and open same document/reference identifiers where available; confirm request scope follows Project B.
3. Switch back to Project A and confirm no stale Project B retrieval dossier appears.
4. Force missing/unapplied scope state and confirm retrieval path fails with explicit scope-required message (no unscoped network call).

## Rollback Notes

- Preferred rollback boundary is entire Phase 2 patch (all frontend retrieval + cache edits) as one unit.
- If emergency partial rollback is required, revert Task 3 first (cache hardening), then Task 2/Task 1 together; do not leave callsites on legacy signature while clients require strict headers.
