# 10-04.5-09-03 Retrieval Scope Regression Verification Matrix and Rollback Protocol

## Objective

Lock in regression protection for the placed-document retrieval failure by codifying automated and manual verification gates, then defining explicit release/rollback decisions at phase boundaries.

## Non-Negotiable Constraints

- Do **not** ship if any strict-scope retrieval gate is red.
- Do **not** accept manual-only confidence without matching automated regression coverage.
- Do **not** roll back scope enforcement while keeping scope-agnostic cache behavior (or vice versa).

## Target Files

- `tests/test_reference_retrieval.py`
- `tests/test_projection_scope_consistency_api.py`
- `tests/test_frontend_scope_client_guards.py`
- `tests/test_claim_queue.py`
- `tests/test_frontend_scope_selector_lock.py`
- `.planning/phases/10-contracts-core-workflow-simplification/10-04.5-09-VERIFICATION.md`

## Phase Gates

- **Gate 3.0 (entry):** `10-04.5-09-01` and `10-04.5-09-02` implementation patches complete.
- **Gate 3.1:** Backend retrieval scope contract tests pass (headers required, scoped project resolution enforced).
- **Gate 3.2:** Frontend header propagation/cache-isolation tests pass.
- **Gate 3.3:** Manual two-project smoke matrix passes with no stale retrieval bleed.
- **Gate 3.4 (release):** Verification artifact + rollback protocol are complete and approved.

## Phase Tasks

### Task 1 - Complete automated regression coverage for retrieval scope contract

Implementation:

1. Extend backend regression suite to cover strict retrieval contract:
   - Missing `X-Project-Id` fails closed.
   - Missing `X-User-Id` fails closed.
   - Correct scoped project succeeds.
   - Wrong project cannot retrieve dossier for same `doc_id`.
2. Extend frontend/client tests to cover retrieval caller strictness:
   - Both retrieval clients send required scope headers.
   - Unscoped retrieval attempts are rejected before HTTP call.
3. Extend cache behavior tests to assert retrieval cache scope keying and scope-switch invalidation.

Dependency:

- Gate 3.0 satisfied.

Verification gate (Gate 3.1 + Gate 3.2):

- All targeted backend/frontend regression test files pass in one run.

Rollback:

- Keep tests in place even if implementation rollback is triggered; tests are the protection against reintroducing this incident class.

### Task 2 - Execute manual two-project verification matrix and capture evidence

Implementation:

1. Create `.planning/phases/10-contracts-core-workflow-simplification/10-04.5-09-VERIFICATION.md` with matrix rows for:
   - Project A success path.
   - Project B success path.
   - Cross-project mismatch path (expect fail-closed/not found behavior).
   - Scope switch A→B→A with retrieval cache isolation check.
2. Record exact commands/steps and observed outcomes for each row.
3. Mark matrix status per row (`pass`/`fail`) with timestamp and runtime stamp context if available.

Dependency:

- Task 1 green.

Verification gate (Gate 3.3):

- Manual matrix shows no `Document <doc_id> not found` false-negative caused by default-project mismatch when scope is correct.
- No stale dossier reappears after scope switches.

Rollback:

- If any matrix row fails, block release and escalate to implementation rollback decision in Task 3.

### Task 3 - Finalize release decision and phase-boundary rollback protocol

Implementation:

1. In `10-04.5-09-VERIFICATION.md`, add explicit go/no-go section tied to Gate 3.1-3.4.
2. Document ordered rollback protocol:
   - Step 1: rollback Phase 2 frontend patch set (`10-04.5-09-02`) if breakage is UI/cache scoped.
   - Step 2: rollback Phase 1 backend patch set (`10-04.5-09-01`) only if backend contract behavior is root issue.
   - Step 3: re-run Gate 3.1-3.3 verification after each rollback boundary.
3. Include explicit prohibition: no partial rollback that leaves frontend expecting strict headers while backend is unscoped, or the inverse.

Dependency:

- Task 2 completed (evidence available).

Verification gate (Gate 3.4):

- Verification artifact contains green/red gate outcomes, release decision, and rollback sequence with re-test requirements.

Rollback:

- This task is documentation/process only; runtime rollback is governed by the protocol it defines.

## Acceptance Criteria

1. Automated tests guard retrieval scope contract end-to-end (backend endpoint, frontend callers, cache behavior).
2. Manual two-project matrix proves retrieval works in correct scope and fails closed in wrong scope.
3. Scope-switch regression (`retrieval_cache` bleed) is explicitly tested and green.
4. A single verification artifact records gate outcomes, evidence, and final release decision.
5. Rollback protocol is phase-boundary based and prohibits mixed-contract partial states.

## Verification Commands

1. `./.venv/bin/pytest tests/test_reference_retrieval.py`
2. `./.venv/bin/pytest tests/test_projection_scope_consistency_api.py`
3. `./.venv/bin/pytest tests/test_frontend_scope_client_guards.py`
4. `./.venv/bin/pytest tests/test_claim_queue.py`
5. `./.venv/bin/pytest tests/test_frontend_scope_selector_lock.py`

## Manual Verification Matrix (to execute and record)

1. In Project A, open retrieval instructions for known placed doc/reference; confirm success.
2. In Project B, repeat with a Project B placed doc/reference; confirm success.
3. Attempt Project A doc under Project B scope; confirm fail-closed behavior (not found/denied per contract).
4. Perform scope switch A→B→A and reopen retrieval instructions; confirm no stale dossier cross-bleed.

## Rollback Notes

- Rollback unit order is strict: Phase 2 frontend first, then Phase 1 backend if necessary.
- After any rollback, rerun all Gate 3.1-3.3 commands before deciding further changes.
- Do not close the incident until verification artifact reflects the final deployed state.
