# 10-04.5 Cleanup: Spine-Only Minimal Corpus Protocol

## Goal

Make the end-to-end workflow reliable on a minimal test corpus while enforcing “spine-only” runtime state (Postgres + object store), and prune local-development residue that breaks multi-user, web-first operation.

This is explicitly a cleanup + hardening pass after 10-04 (durable decisions/events) and before 10-05 (demo/trace replay).

## Success Criteria

- A minimal corpus can be ingested, processed, reviewed, and navigated with *no required local disk state* beyond container runtime.
- All user-facing state that must persist across refresh/restart is stored in the spine.
- The system supports concurrent reviewers without shared global/session coupling (project_id + created_by_user_id are first-class).
- A scripted protocol exists to validate each stage and pinpoint failures quickly.
- Local-only residue is either deleted or gated behind explicit dev flags.

## Non-Goals

- Building a new UI stack (non-Streamlit) in this plan.
- Adding new ML capabilities (better models, new rerankers, etc.).
- Perfect citation resolution (OpenAlex/Crossref ambiguity) beyond stability and clear failure modes.

## Minimal Test Corpus

Define a “workflow corpus” of 3 citing PDFs (small, fast, representative). Use whatever is available and stable; the corpus must be:

- small enough to process quickly
- includes citations that produce requested works
- includes at least one cited PDF that can be uploaded once and reused across multiple citing claims

Corpus policy:
- If stored in-repo, use Git LFS or a separate download step.
- If not stored in-repo, provide paths via env vars and document the expected location.

## Stage-Wise Protocol (What Must Work)

The protocol is the product for this plan: a checklist + verifier scripts that run each stage independently.

### Stage A: Ingestion (upload + document record)

Expected:
- `/ingest` upload creates an ingest document row with stable id.
- PDF blobs land in object store; no coupling to local paths.

Checks:
- Upload N PDFs; verify `/ingest` list returns them.
- Verify object keys exist; verify metadata has project_id.

### Stage B: Extraction (text + references)

Expected:
- `/ingest/{doc_id}/extract` reaches `complete` and stores extraction data.
- `force=true` re-extract works for diagnosis.

Checks:
- Ensure extraction data is present and stable across restart.

### Stage C: Resolution (reference targets)

Expected:
- `/ingest/{doc_id}/resolve` produces reference ids/targets.
- Failure modes are explicit (e.g., unresolved targets are still represented).

Checks:
- Confirm at least one citing sentence yields a “requested works” queue entry.

### Stage D: Attachments (cited PDF pipeline)

Expected:
- Upload cited PDFs into attachments store; pipeline reaches `matched` or `error`.
- One cited PDF can be reused across many citing claims via attachment cloning (no mutation of the global source row).
- Promotion to ingest exists when needed and is idempotent.

Checks:
- Upload one cited PDF; assign it to two separate citing claims and verify clones exist.

### Stage E: Evidence (retrieval + decisions/events)

Expected:
- Evidence runs can be triggered and viewed per claim.
- Decisions are durable events (10-04) and persist across refresh.
- Auto-rerun triggers after attachment placement/clone (best-effort).

Checks:
- Pin/accept/reject persists after page reload and server restart.

### Stage F: Graph / Surfing (navigation surface)

Expected:
- Graph nodes reflect availability once a reference is linked to an ingest id.
- Doc-level association persists: a single “ref -> ingest” link enables auto-place and graph visibility without re-running resolution.

Checks:
- After assigning a cited PDF to a reference, graph shows cited work as “available” for that target.

## Cleanup / Pruning Targets

Remove or gate anything that assumes:

- local filesystem persistence under `data/**` as the source of truth
- Streamlit session state as the durable store for reviewer work
- single-user implicit global state (e.g., “default” project without project_id in records)

Concrete pruning tasks:

1) Inventory “local-only stores”
- Identify any files/dirs that are still treated as authoritative state.
- Confirm whether they are legacy compat (should be removed) or caches (ok to keep as optional).

2) Ensure spine ownership fields are consistent
- Every spine table row: confirm `project_id` + `created_by_user_id` (where applicable).
- Every endpoint: confirm project_id selection is explicit and consistent.

3) Remove or hard-gate dev affordances
- Seed scripts, toy datasets, local-only shortcuts.
- Dev-only feature flags must not affect production correctness.

4) Normalize attachment lifecycle for multi-user
- “Global” attachments remain global; claim/doc placements are clones.
- Promote-ingest is the only bridge from attachment PDF to ingested Work.

5) Verify idempotency boundaries
- Re-running extract/resolve, re-placing attachments, and re-triggering evidence should not corrupt state.
