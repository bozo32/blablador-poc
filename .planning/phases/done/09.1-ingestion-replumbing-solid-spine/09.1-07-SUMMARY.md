# Phase 9.1 Plan 07: Scope Plumbing (project_id + user_id) Summary

**Added foundational scoping so all new ingestion spine rows are tagged with `project_id` and `created_by_user_id`, and the API propagates scope (defaulted for the POC) without breaking existing UI flows.**

## Accomplishments

- Added `DEFAULT_PROJECT_ID` and `DEFAULT_USER_ID` settings (env overridable)
- Extended Postgres spine schema (`works`, `attempts`, `jobs`, `artifacts`) with:
  - `project_id` (default `default`)
  - `created_by_user_id` (default `local`)
  - idempotent `ALTER TABLE ... ADD COLUMN IF NOT EXISTS ...` so existing DBs migrate safely
- Updated spine helpers to write scope columns and filter attempt/work lookups by `project_id`
- Updated ingest + extract flows (API endpoint and background pipeline) to propagate scope
- Added `project_id` to legacy ingestion metadata and to the ingest response model (non-breaking)

## Verification

- Ran `bash scripts/dev/up.sh` and ingested a fresh PDF
- Confirmed Postgres rows for the new work have non-empty scope columns:
  - `works.project_id` / `works.created_by_user_id`
  - `attempts.project_id` / `attempts.created_by_user_id`
  - `jobs.project_id` / `jobs.created_by_user_id`
  - `artifacts.project_id` / `artifacts.created_by_user_id`

## Notes / Known Limitations

- Current `works` table remains keyed by `work_id` only; true “global works + per-project membership” lands in the next identity-split plan (09.1-08).
