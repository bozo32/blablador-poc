# Phase 9.1: Ingestion Replumbing + Solid Spine (INSERTED)

## Why This Phase Exists

Phase 9 introduced richer navigation and automation pressure (graph-driven workflows, background runs, multi-step pipelines). The current single-machine filesystem-first ingestion works, but it is brittle across host platforms and makes it hard to move heavy services (GROBID, OCR/doc parsing, model servers) to remote Linux boxes.

We need a stable execution spine (jobs/attempts/provenance/artifacts) and a portable runtime so ingestion can be automated reliably, debugged, and scaled without rewriting the product logic.

## Primary Goal

Make ingestion runnable and repeatable across machines by introducing:

- A Docker/Compose runtime for the app + infra.
- A durable job/attempt model with explicit states and idempotency.
- Object-store-backed artifacts (S3-compatible) and Postgres metadata so workers can run remotely.
- Clear internal service boundaries (GROBID, fallback extraction/OCR, model gateway).

## Constraints

- Keep the POC working throughout (incremental changes, rollback-friendly).
- Avoid big-bang migrations; allow transitional dual-write where needed.
- Keep user-auth out of scope; use internal service tokens only.

## Entry Criteria

- Current backend+frontend start and basic ingestion works.

## Exit Criteria

- `docker compose up --build` brings up a working stack on a fresh machine.
- Uploading a PDF triggers an end-to-end ingestion run with persisted job state.
- Artifacts live in S3-compatible storage; job metadata in Postgres.
- GROBID and fallback extraction can run as separate services (and can be moved to a remote Linux host by changing config).
