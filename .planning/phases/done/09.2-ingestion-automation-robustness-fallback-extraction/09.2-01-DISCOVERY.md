# Phase 9.2.01 Discovery: Ingestion Robustness + Fallback Extraction

## Goal

Make ingestion resilient and automatable when GROBID (or TEI) fails, by offering a user-visible fallback that can still produce usable body text and a bibliography (with uncertainty labels).

## Non-Goals (for this phase)

- Perfect TEI structure for all PDFs.
- Fully general citation linking with zero ambiguity.

## Clarifying Questions (Answer These First)

### 1) What does "handles anything" mean for scanned PDFs?

- Do we include OCR as part of the fallback (yes/no)?
- If yes: do we accept slower extraction (tens of seconds/minutes) for scanned docs?

Recommended default: Yes OCR (opt-in button), allow slow path, label output provenance.

Locked update: OCR is part of fallback by default on primary failure (hybrid per-page), runs async, and is cancellable/retryable.

### 2) Where does fallback output live and how is it used?

- Should fallback write into the existing ingest document record (new stage like `text_extraction` / `fallback_extraction`), or stay ephemeral per-request?
- Should Surfing/Chasing/evidence pipelines consume fallback text automatically, or only after user opt-in?

Recommended default: Persist as a new stage on the ingest document, opt-in per document when full extraction fails.

Locked update: Persist as a versioned attempt/stage on the Work (Phase 9.1 spine: Postgres metadata + object store artifacts). Fallback auto-runs on primary failure; UI also offers "force fallback" even if primary succeeds.

### 3) Bibliography source-of-truth when GROBID header fails

- Should we always try `processReferences` even when `processHeaderDocument` 500s (yes/no)?
- If references-only succeeds, is that good enough to proceed without header merge?

Recommended default: Yes; references-only is acceptable; store header failure as a quality flag.

Locked: Yes; always attempt refs-only; merge best-of-breed outputs (GROBID refs + fallback body) with per-field provenance.

### 4) Preferred fallback stack (dependency + ops constraints)

- Are you okay adding a new dependency (e.g. `pymupdf` / `docling`) to the backend runtime?
- Should fallback run server-side only, or can it run client-side in Streamlit for local-only POC?

Recommended default: Server-side PyMuPDF for text spans; add docling later if needed.

Locked update: Start with server-side PyMuPDF for text-layer fallback. OCR/docling integration may live in a separate worker service/container so NumPy/Pandas constraints do not break the main app runtime.

### 5) Output contract (minimum viable structure)

For fallback output, which of these are required?

- Body text only (single string)
- Page-bounded text spans with bboxes (for highlighting)
- Paragraph-ish grouping for windowing (needed for current chunking semantics)
- Reference list entries (structured: doi/title/year/authors)
- In-text citation detection + linking to bib entries (probabilistic)

Recommended default MVP: body text + page breaks + reference list entries + quality flags. Defer bbox/highlighting + citation linking until the pipeline is stable.

Locked update: store both `pages[]` and joined `body_text`, plus per-page provenance and attempt metadata.

### 6) UX: when and how the option appears

- Only show the fallback button when full extraction fails?
- Also allow manual "use fallback" even when full extraction succeeds (for low-quality TEI)?

Recommended default: Show only on failure initially; add manual override later.

Locked update: expose manual "force fallback" now.

### 7) Success criteria (so we can stop)

- Coverage target: e.g. ">=95% of uploaded PDFs yield *some* body text"?
- What should happen to resolution + graph indexing when only fallback text exists?

Recommended default: body text success >=95% on a small local corpus; keep reference resolution tied to reference extraction quality.

Locked update: define the corpus as a small mixed local set and track overall + per-class; gate resolution via a resolution-time prompt when refs quality is low.

## Proposed Work Breakdown (pending answers)

1. Define a new ingest stage schema for fallback results + quality flags.
2. Add backend endpoint to trigger fallback extraction for a doc.
3. Implement fallback extractor (PyMuPDF first) with clear provenance.
4. Implement reference-only extraction fallback (GROBID refs) when header/fulltext fails.
5. Add Streamlit UI button and failure messaging.
6. Add tests for: GROBID header 500 case + fallback success.
